  ## Q1 — Does published max-pressure subtract downstream, and are we missing it?
  
  **Yes — confirmed from three independent sources, and yes, this is a real gap in our controller.**
  
  - sumo-rl's actual source (`sumo_rl/environment/traffic_signal.py`):
  ```python
  def get_pressure(self):
      """Returns the pressure (#veh leaving - #veh approaching) of the intersection."""
      return sum(getLastStepVehicleNumber(lane) for lane in self.out_lanes) - sum(
          getLastStepVehicleNumber(lane) for lane in self.lanes)
  ```
  - RESCO paper (Ault &amp; Sharon, NeurIPS'21 D&amp;B): "MPLight utilizes the concept of pressure... Pressure is the difference in queue lengths from incoming lanes of an intersection and the queue length on a downstream intersection's receiving lane."
  - PQ-MP (Liu, Gayah, Levin, arXiv:2406.19305, 2024): weight of a movement = upstream count *minus* turn-ratio-weighted average of downstream movement counts (Eq. 5), the textbook Varaiya (2013) formulation.
  
  The whole point of subtracting downstream occupancy is spillback prevention: max-pressure won't green a phase that would push vehicles into an already-full receiving lane, even if upstream demand is high. An upstream-only weighted controller (what we have) can't see this — it will happily serve a phase whose downstream is jammed. **Concrete fix to consider:** add a downstream-queue term (weighted by turn-ratio if lane-level turn data is available, else simple downstream-occupancy subtraction) to the pressure/weight calculation, at least for the phases where downstream lane state is observable.
  
  ## Q2 — How do serious projects evaluate?
  
  Standard metrics across RESCO/LibSignal/sumolights: **average travel time, average delay (real-time proxy = current speed vs. max allowed speed, since true delay is only computable in hindsight), total/average queue length, throughput (trips completed)**. RESCO's reward-weight vector literally exposes these five as tunable weights: `[travel_time, approx_delay, wait_time, queue_length, pressure]`.
  
  Standard baselines: **Fixed-time/pre-timed** (cycle from the SUMO scenario), **Max-pressure** (Chen et al. formulation), **Greedy** (max queue length + approaching count, Ma &amp; Wu). RL controllers are compared against all three, not just against each other.
  
  Evaluation methodology worth stealing: RESCO uses **real-world calibrated demand scenarios** (TAPAS Cologne, InTAS Ingolstadt, Germany) at **three deliberately increasing scales** — single signal → arterial corridor → multi-intersection region — rather than one synthetic grid. It also explicitly varies sensing-realism assumptions (full-state vs. 50m-radius vs. stopped-queue-only) and finds that **claimed SOTA RL algorithms often lose to a plain decentralized IDQN once sensing is realistic and intersections are non-stylized** — a useful caution before ever adding RL on top of our controller.
  
  Gap in the field, in our favor: none of these standard suites report **percentile waits (90th/99th, max-wait)** — everything is mean-based (avg delay, avg travel time). Our max-wait force-serve / bounded-starvation guard is evaluating something the "serious" literature mostly doesn't measure.

  ## Q4 — Pedestrian demand in these controllers?
  
  Not in any of the popular open-source repos — sumo-rl, CityFlow, RESCO, LibSignal, Flow, CoLight/PressLight/FRAP/MPLight are all **vehicle-only**. Pedestrian-aware max-pressure exists only in recent papers, generally without public code:
  
  - **PQ-MP** (Liu, Gayah, Levin, Penn State/UMN, arXiv:2406.19305, June 2024): adds a pedestrian pressure term = crosswalk queue minus downstream-averaged crosswalk queue, weighted by a tunable λ∈(0,1) so pedestrian pressure (higher density than vehicles) doesn't dominate; **also discounts right-turn vehicle saturation flow proportionally to conflicting pedestrian crossing volume**, modeling yield behavior explicitly. Proves max-stability extends to the pedestrian-augmented model. No GitHub code found.
  - Baseline it beats, **Xu et al. 2023's rule-based MP**: runs vehicle-only queue-based max-pressure normally, but forces a **protected pedestrian phase once the first-arrived pedestrian's wait exceeds a threshold**. This is structurally the closest published analog to our own pedestrian-wait-bound / force-serve mechanism — worth citing as validation that our approach matches a real academic pattern, even though it predates and is simpler than PQ-MP.
  
  Stealable mechanic even without full pedestrian-pressure: **discount right-turn saturation/service rate while pedestrians are actively crossing**, rather than treating right turns as pedestrian-blind.

  ### 1. mihir-m-gandhi/Adaptive-Traffic-Signal-Timer (202★)
  **Approach:** YOLO object detection on camera images at each approach → counts by class (car/bike/bus/truck/rickshaw) → weighted formula (per-class weights + lane count + avg speed) sets green time. Includes a from-scratch Pygame simulation module. Published at IEEE ICRAIE 2020.
  **Clever:** Per-vehicle-class weighting (not just raw count) is the most "textbook-correct" density formula in the whole search — closest thing to a canonical reference implementation everyone else in this space copies.
  **Weakness:** Fixed additive formula, no fairness/starvation bound mentioned, no emergency vehicle handling, no closed loop with real hardware — pure simulation + still image inference, not live video.
  
  ### 2. docwza/sumolights (336★)
  **Approach:** SUMO-only (no camera/vision) implementations of DQN, DDPG, Webster's, **Max-pressure**, and Self-Organizing Traffic Lights, built for an academic benchmarking paper (arXiv:1909.00395).
  **Relevance:** This is the closest thing to a real Max-pressure implementation in the search — confirms max-pressure control is well-trodden in the *simulation* literature, but it consumes ground-truth SUMO lane occupancy, never real camera-derived counts.
  
  ### 3. AndreaVidali/Deep-QLearning-Agent-for-Traffic-Signal-Control (505★)
  **Approach:** DQN agent learns phase selection in SUMO. Most-starred repo in the entire traffic-signal-control GitHub space. No vision component at all — pure RL-on-simulator baseline that most other projects (including several below) fork ideas from.
  
  ### 4. anmspro/Traffic-Signal-Violation-Detection-System (485★)
  **Approach:** YOLOv3 + Tkinter GUI, detects vehicles crossing the stop line on red. This is enforcement/violation detection, not adaptive control — adjacent problem, same detector stack. Notable for being the single most-starred "traffic + YOLO" GitHub project overall, which tells you where community attention in this space actually goes (enforcement demos, not control systems).

  **Weakness:** Repo is archived/dead since 2021, MIT badge shown but GitHub API reports no license file, and given the pattern seen in #11 below (README overselling actual code), the depth of the "waiting time per vehicle" claim is unverified — treat as an aspirational description, not confirmed working logic.
